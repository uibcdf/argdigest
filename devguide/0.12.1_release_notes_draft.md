# 0.12.1 — release notes

**Status:** tagged 2026-09-01.
**Shape:** three fixes, no new API and no breaking change. Two of them are one story —
a rule and the false positive it shipped with — and the third is a diagnostic that was
defined in the catalog and never emitted. This is the patch two downstream libraries
declared a floor against before it existed.

---

## Fixed — an alias and its canonical name are alternatives; a default is neither

`0.12.0` accepted `f(atom_name=…, atom_names=…)` in silence. Declared normalization
renames the alias onto its target, so the second write landed on the same key and the
first value disappeared before any digester saw it. One of the two arguments the caller
passed simply did not arrive, with nothing raised and nothing logged.

`c46cd01` closed that: an alias supplied together with its canonical name, or two aliases
pointing at one target, now raise `ArgumentConsistencyError` before normalization can
discard a value.

**And it shipped with a false positive that was worse than the defect.** The rule judged
collisions on the names present in `bound`, but `bind_arguments` calls `apply_defaults()`
before returning, so a parameter resting on its signature default is indistinguishable
there from one the caller wrote. **Every alias whose target has a default became a
collision.** MolSysMT hit it immediately:

```python
msm.compare(molsys_A, molsys_B, attributes_type='topological')
# 0.12.0 + c46cd01: ArgumentConsistencyError naming `attribute_type` and
#                   `attributes_type`, for a call that passed exactly one of them
```

Four MolSysMT tests failed on it, including the one written to cover that alias.
`87bd20b` fixes the input rather than the rule: `bind_arguments` now reports the names
the caller actually supplied, recorded before defaults are applied, and the collision
check reads those.

The two commits are a pair and only make sense together. A consumer that adopted
`c46cd01` alone would trade a silent wrong answer for a loud wrong error.

## Fixed — the two contract warnings reach the catalog they were defined in

`ARG-WARN-MISS-001` and `ARG-WARN-CONTRACT-001` existed in the catalog and had never
appeared in a single event. Both call sites built a catalog warning and handed it to
`warnings.warn`, so the event reached SMonitor only through `logging.captureWarnings` and
the `py.warnings` logger — with `code=None`, `source="py.warnings"`, no `category` and
none of the structured fields.

Anything keyed on codes was therefore blind to them: `events_by_code`, fingerprint
summaries, and the QA policies the MolSysSuite pytest work is built around.

The comment at the second call site — *"Always issue standard Python warning for
testing/simple setups"* — described a real constraint at the time: `warn()` returned
without warning once it found a catalog entry, so routing through the bundle would have
removed the Python warning that test suites and user filters depend on. `smonitor 0.13.0`
removes the constraint by raising the Python warning as well as emitting the event, which
is why this fix and that floor arrive together.

## Changed — `smonitor >= 0.13.0`

Catalog exceptions and warnings changed shape in that release: `warn()` raises the Python
warning as well as emitting the event, and `args` no longer carries the appended hint,
which is what makes an instance survive being rebuilt by `pickle`, `copy.deepcopy` or a
test-runner boundary. Earlier versions do not behave that way, and **the difference is
silent rather than an import error** — which is what makes the floor necessary rather
than advisory.

## Fixed — the install instructions named a route that does not exist

The README and the installation page both told users to `pip install argdigest`. There is
no PyPI release and no workflow that would produce one; the `uibcdf` conda channel is the
only release route there has ever been. Both pages now document that route, with
`-c conda-forge` alongside `-c uibcdf` because `depdigest` and `smonitor` resolve from the
first.

## Infrastructure — the compatibility guard derives its floors

The compatibility tests typed `smonitor>=0.11.4` into three assertions, so raising the
floor in `7a97cab` — correctly, in both manifests — turned CI on `main` red for a change
that was right, and it stayed red until `8099b74`.

They now derive from `pyproject.toml` and check the conda recipe and the documented
compatibility matrix against it. Raising a floor everywhere passes; raising it in one
place fails. Mutation-verified in all four directions, including the legitimate change
that used to fail.

Rewriting them surfaced what the old shape could not see: the documented compatibility
matrix still stated `smonitor 0.11.4`, agreeing with the tests and with neither manifest.

`0514b86` also updates the actions used by the conda publication workflow.

## For downstream

`molsysviewer` and `molsysmt` both declare `argdigest>=0.12.1` and were waiting for this
tag. Take the pair of normalization fixes together: the collision rule without its
false-positive correction is not a state anyone should install.
